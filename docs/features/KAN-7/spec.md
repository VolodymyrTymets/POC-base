# KAN-7 — Replace eslint with Oxlint

## Problem
`api/` lints TypeScript with ESLint 9 (flat config, `eslint.config.mjs`): `eslint.configs.recommended` +
`typescript-eslint`'s `recommendedTypeChecked` + `eslint-plugin-prettier`, run via
`pnpm --dir api run lint` (`eslint "{src,apps,libs,test}/**/*.ts" --fix`). The ticket asks to replace this
with Oxlint, a Rust-based linter, for faster lint runs — no behavioural bug is being fixed, this is a
tooling swap.

## Goal / business value
Serves ranked goal 1 (project scaffolding, `BUSINESS_MODEL.md`) — a faster, lower-friction lint step is
part of keeping this base "clonable and understandable in under a day" for whoever forks it next; it does
not touch the domain (goals 2/3 unaffected).

## Scope
- in: swap the linter from ESLint to Oxlint for `api/`'s existing `lint` script — new `.oxlintrc.json`
  (migrated from the current flat config), `api/package.json` script + devDependency changes, removal of
  `eslint.config.mjs` and all eslint-family devDependencies, and updating the two docs that name
  `eslint.config.mjs` by path (`.claude/rules/js-tooling.md`, `docs/RUNBOOK.md`).
- **out (explicit):**
  - **Type-aware linting** (`typescript-eslint`'s `recommendedTypeChecked`, the `no-floating-promises`/
    `no-unsafe-argument` overrides). Oxlint supports this only via the separate `oxlint-tsgolint` package
    (a Go binary, 59/61 rule parity) — human decision (plan approval round): ship Oxlint's standard
    (non-type-aware) rule set now; type-aware parity is a follow-up, not this ticket.
  - Formatting. Prettier already runs standalone (`pnpm --dir api run format`); Oxlint is a linter, not a
    formatter (`oxfmt` is a separate, unrelated tool). The current `eslint-plugin-prettier` integration
    (which surfaced Prettier issues as lint errors) is dropped along with ESLint itself — Prettier's own
    script is unaffected and remains the only formatting check.
  - Fixing the pre-existing lint violations (real ESLint baseline as installed today: 581 errors / 39
    warnings — the `docs/RUNBOOK.md` figure of 60/5 was itself stale before this ticket, from dependency
    drift). Oxlint's rule set differs, so the violation count will change regardless; this ticket
    documents the new baseline, it does not chase it to zero (rule B4/C1 — same boundary KAN-8 drew for
    the Customer-model bug).
  - `.github/workflows/agent-checks.yml`. Its suppression-comment guard pattern-matches the literal string
    `eslint-disable`; Oxlint's native suppression comment is `oxlint-disable` (confirmed via Context7 —
    oxc.rs docs), which that regex will not catch. CI/pipeline files are only changed in a dedicated PR
    with a human reviewer (rule T4) — this is flagged as a follow-up, not fixed here.
  - `apps/`, `libs/` in the lint script's glob — both are already-absent directories left over from the
    Nest starter template; kept as-is (no opportunistic cleanup, rule C1).

## Acceptance criteria
- [x] AC1 `oxlint` added as an `api/package.json` devDependency; `eslint`, `@eslint/js`,
      `@eslint/eslintrc`, `eslint-config-prettier`, `eslint-plugin-prettier`, `typescript-eslint`, and
      `globals` removed. Verified: `pnpm remove` output confirmed all seven removed; `pnpm add -D oxlint`
      confirmed added; lockfile regenerated by pnpm (rule T3).
- [x] AC2 `api/eslint.config.mjs` deleted (`git rm`); `api/.oxlintrc.json` added, generated via
      `@oxlint/migrate` and hand-reviewed: `no-explicit-any` is correctly absent (matching the old
      `'off'` — Oxlint doesn't enable it without an explicit entry), all 23 type-aware rules were
      correctly excluded by the migrate tool, and the `jsPlugins`/`eslint-plugin-prettier` bridge the
      tool added was removed by hand (see `ADR-0007` point 2 — formatting stays Prettier-only).
- [x] AC3 `api/package.json`'s `lint` script runs `oxlint` instead of `eslint`, targeting the same scope
      the old glob covered (`src`, `test`). **Amended mid-implementation** (see `ADR-0007`): `lint` is
      check-only, not `--fix` — `oxlint --fix` was found to silently strip a load-bearing type cast with
      no diagnostic trail, so auto-fixing moved to a separate, manually-run `lint:fix` script instead of
      the ESLint-era 1:1 `--fix` parity originally planned.
- [x] AC4 `pnpm --dir api run lint` executes end-to-end: exit 1, 10 real errors (`no-unused-vars` ×8,
      `no-require-imports` ×1, plus one more `no-unused-vars`), all pre-existing code-quality issues, none
      introduced by this change. Down from the real ESLint baseline of 581 errors / 39 warnings — expected
      per the dropped type-aware rules, not a cleanup (see `ADR-0007`).
- [x] AC5 `.claude/rules/js-tooling.md` (rules 4 and 7) and `docs/RUNBOOK.md`'s lint row in "Known
      failures" updated to describe Oxlint, the real (previously-stale) baseline, and the new
      `eslint-disable`-vs-`oxlint-disable` CI guard gap.
- [x] AC6 `docs/decisions/ADR-0007-oxlint-linter.md` written, recording the decision, the precedent it
      follows, the deferred-type-aware-linting follow-up (OQ1), and the mid-implementation `--fix` finding.

## Edge cases
| Case | Expected behaviour | Decided by |
|------|--------------------|-----------|
| `@oxlint/migrate` doesn't have a 1:1 mapping for an existing ESLint/typescript-eslint rule | Drop the unmapped rule rather than hand-invent an Oxlint equivalent; note any dropped rule in the plan's risk table | assumption |
| Oxlint reports a different error/warning count than ESLint's current 60/5 baseline | Expected and acceptable — record the real new count, do not tune rules to chase parity (see out-of-scope) | ticket scope |
| A file currently has an `eslint-disable` comment | Leave it — Oxlint ignores comments it doesn't recognize; only re-suppress with `oxlint-disable` if Oxlint newly flags that exact line, and only with a `WHY:` per rule B3 | assumption |
