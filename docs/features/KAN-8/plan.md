## Contract changes

## Requirements (ordered, each independently verifiable)

### R1 — pnpm as the declared package manager (S)
- files: `api/package.json` (change: add `packageManager` field), `api/pnpm-workspace.yaml` (new)
- layer: tooling config
- test: none (config only) — proven by R2's install succeeding
- executed how: `pnpm --dir api install` runs without falling back to an unpinned pnpm version
- risk: none

### R2 — Declare the four accidental-hoisting dependencies (S)
- files: `api/package.json` (change: add `lodash`, `ms`, `keyv`, `@prisma/driver-adapter-utils` to
  `dependencies`, versions matched to what's already resolvable/imported in `src/`)
- layer: tooling config
- test: `pnpm --dir api exec tsc --noEmit` no longer reports "Cannot find module" for these four
- executed how: `pnpm --dir api install && pnpm --dir api run build` — build reaches the pre-existing,
  unrelated Customer-model error (OQ1) and no further, i.e. no new missing-module errors
- risk: a pulled transitive version conflicts with an existing one — mitigated by installing and running
  the full test suite before moving on

### R3 — Generate the lockfile and remove yarn's (M)
- files: `api/pnpm-lock.yaml` (generated by `pnpm install`, not hand-written — rule T3), `api/yarn.lock`
  (removed)
- layer: tooling config
- test: none directly
- executed how: `pnpm --dir api install` (writes the lockfile); `git rm api/yarn.lock`; re-run install
  from a clean `node_modules` to confirm the lockfile alone is sufficient
- risk: none — this is what T3 requires (dependency manager owns and regenerates its own lockfile)

### R4 — Dockerfile and migration entrypoint use pnpm (M)
- files: `api/Dockerfile` (change: `RUN yarn install` → `RUN corepack enable && pnpm install
  --frozen-lockfile`; `CMD ["yarn", "start"]` / `CMD ["yarn", "worker:start:dev"]` → pnpm equivalents;
  `COPY package*.json ./` → also copy `pnpm-lock.yaml`/`pnpm-workspace.yaml`), `api/docker-prisma-migration.sh`
  (only if it invokes yarn/npx in a way that needs updating — currently uses `npx`, which stays)
- layer: infra/build
- test: none directly
- executed how: `docker compose up -d --build` — boots `api`, `worker`, `postgres`, `redis`; this is also
  how R6/R7 get their real runtime, since local host Node (v24.16.0) doesn't match the pinned 22.16.0 and
  no local v22 is available (rule T2 — see OQ2, confirm in approval)
- risk: `COPY package*.json ./` predates the lockfile copy — must fix or the Docker build installs against
  a stale/absent lockfile

### R5 — README, launch.sh, and package.json scripts (S)
- files: `api/README.md` (change: every `yarn ...` command block → `pnpm ...`), `api/launch.sh` (change:
  `yarn worker:start:dev` / `yarn start:dev` → pnpm equivalents), `api/package.json` (change: `test`,
  `test:e2e`, `test:debug` scripts — replace the yarn-shim-specific `node_modules/.bin/jest` form with
  `jest` resolved via pnpm, matching what the command map already runs directly)
- layer: docs / tooling config
- test: `pnpm --dir api run test` and `pnpm --dir api run test:e2e` succeed when invoked directly (not
  just via the `pnpm exec jest --config ...` workaround)
- executed how: run both commands, capture output
- risk: none

### R6 — Verify: install, build, boot (M)
- files: none (verification only)
- layer: n/a
- test: n/a
- executed how (all via `docker compose up -d --build`, per OQ2): confirm `api` serves `/graphql` and a
  real query/mutation succeeds; confirm `worker` boots without error in its logs
- risk: the pre-existing Customer-model bug (OQ1) still breaks `tsc --noEmit`/`build` — expected, not a
  regression from this ticket; capture the exact error to prove it's the same known one

### R7 — Verify: tests (S)
- files: none
- layer: n/a
- test: full unit + e2e suite
- executed how: `NODE_OPTIONS=--experimental-vm-modules pnpm --dir api exec jest --config ./test/jest.json`
  and `--config ./test/jest-e2e.json`, run inside the Docker `api` container (or against it) to match the
  pinned runtime; report pass/fail counts and confirm the only failure is the known `sign-in-otp` one
- risk: none beyond OQ1
